1 · Grammar Input Format

Write one production rule per line. Use the arrow -> to separate the left-hand side (LHS) non-terminal from the right-hand side (RHS). Use the pipe | to list alternative productions on the same line.

E  -> T EP
EP -> + T EP | ε
T  -> F TP
TP -> * F TP | ε
F  -> ( E ) | id

Symbol Conventions

Symbol typeRuleExample
Non-terminalStarts with an uppercase letterE, EP, Stmt
TerminalAnything else (lowercase, digit, special)id, +, (
Empty / εε, eps, or epsilonA -> ε

Symbols in a production are separated by whitespace. Single-character symbols can also be entered run-together in the test string (e.g., aab is treated as tokens a a b).

2 · Using the RDP Module

Loading the grammar

  1. Navigate to the Recursive Descent Parser page from the home screen.
  2. Type (or paste) your grammar in the Grammar Input text area, or choose one of the built-in examples from the drop-down.
  3. Enter a Test String in the second field.
  4. Click ▶ Load & Simulate. The full trace is computed instantly.

Step controls

ButtonAction
Next →Advance one simulation step forward.
← PrevGo back one step.
▶ PlayAuto-advance with the delay set by the slider.
⏸ PauseStop auto-play.
↦ EndJump directly to the final state.
⟳ ResetClear everything and start over.

Reading the parse tree

ColourMeaning
Purple borderNon-terminal node (not yet expanded or successfully returned)
Green fillTerminal node that has been matched, or a non-terminal that returned success
Orange glowNode currently being expanded
Red fillNode that failed; will be removed on backtrack
Dashed circleε (empty) production

Input token strip

The token strip above the parse tree shows all input tokens. The blue token is the one currently being examined. Green struck-through tokens have been consumed. Grey tokens are yet to be read.

Call stack

The Call Stack panel shows the current recursion depth — the topmost entry is the non-terminal being expanded right now. Entries below it are the calling context that will resume after the current expansion returns.

3 · LL(1) — First & Follow Computation

  1. Enter the grammar on the left panel and click ▶ Load Grammar.
  2. Switch to the ① First & Follow tab (it may already be active).
  3. The parsed rules are shown in the left panel for reference.

Step-by-step mode

Click Next Step → to add one element to a FIRST or FOLLOW set at a time. The step explanation box below the controls shows exactly which rule caused the derivation and why. The affected set card pulses blue to draw attention.

Compute All

Click Compute All to fill every FIRST and FOLLOW set at once. The full derivation log appears in the trace panel below.

Understanding the sets

  • FIRST(A) = the set of terminals that can begin any string derived from A, plus ε if A can derive the empty string.
  • FOLLOW(A) = the set of terminals (and $) that can appear immediately after A in some sentential form. $ always appears in FOLLOW(start symbol).

4 · LL(1) — Parse Table Construction

Switch to the ② Parse Table tab. The table is ready to be filled once First & Follow sets are available (you don't need to manually complete them first; they are computed automatically when you load the grammar).

Step-by-step filling

Click Next Step → to place one production into the table. Each step highlights the filled cell and explains why that cell was chosen (from FIRST or FOLLOW). Use Fill All to fill all cells at once.

Conflict detection

If a cell would receive two different productions, a red conflict banner appears at the top of the table, and the conflicted cell is highlighted in red with a ⚠ marker. This means the grammar is not LL(1) — no LL(1) parser can be built for it directly. You may need to eliminate left recursion, left-factor the grammar, or use a different parsing strategy.

5 · LL(1) — String Parsing

Switch to the ③ String Parsing tab. Enter a test string in the input field and click Parse.

Stack / Input / Action trace

The classic three-column LL(1) trace is shown: Stack (top on the right), Remaining Input, and Action (which rule was applied or which terminal was matched). Each row corresponds to one move.

Step controls

Use Next Step →, ← Prev, ▶ Play, and ↦ End as in the RDP module. The live stack and input displays above the trace update with every step.

Verdict

The final row is marked ACCEPT if the input was fully consumed and the stack reduced to just $, or REJECT with the reason (e.g., "no entry in M[NT, token]" or "stack empty but input remaining").

6 · Example Grammars

Arithmetic E→T EP; EP→+T EP|ε; T→F TP; TP→*F TP|ε; F→(E)|id Classic LL(1)-compatible expression grammar
Simple S→a B|b; B→b B|ε Small, easy to trace by hand
Palindrome-like S→a S b|ε Matches aⁿbⁿ
Conflicted S→a|a b NOT LL(1) — demonstrates conflict detection

7 · Limitations & Tips

  • Left recursion: The RDP simulator will loop infinitely on left-recursive grammars (e.g., E → E + T). Remove left recursion before using it.
  • LL(1) restrictions: The LL(1) module will detect conflicts but cannot automatically fix them. You must left-factor or eliminate left recursion manually.
  • Token separation: For multi-character terminals like id, use spaces in the test string: id + id * id. For single-character grammars, you can write them run-together: aabb.
  • Performance: All computation is done in the browser with no server calls. Very large grammars (dozens of rules) may take a moment but will still work.
  • Cycle detection: The FIRST/FOLLOW algorithm uses a fixed-point iteration that terminates for any grammar, including cyclic ones.
  • Browser: Works in any modern browser (Chrome, Firefox, Edge, Safari). No installation required.
